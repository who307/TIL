## 1. Git과 GitHub는 뭐가 다른가

* **한 줄 비유**: Git은 내 컴퓨터에 있는 **"게임 세이브 기능"**, GitHub는 그 세이브 파일을 올려두는 **"인터넷 사물함"** 임.
* **Git**: 파일이 언제, 어떻게 바뀌었는지를 기록하는 **프로그램**. 내 컴퓨터 안에서만 동작함.
  * 숙제를 하다가 "여기까지 저장" 버튼을 누르면, 나중에 망쳐도 그 시점으로 되돌아갈 수 있는 것과 같음.
* **GitHub**: Git으로 기록한 내용을 **인터넷에 올려두는 웹사이트**.
  * 컴퓨터가 고장 나도 기록이 남아 있고, 친구들과 같은 프로젝트를 함께 볼 수 있음.

| 구분 | Git | GitHub |
| :--- | :--- | :--- |
| 정체 | 프로그램 | 웹사이트(서비스) |
| 위치 | 내 컴퓨터 | 인터넷 |
| 하는 일 | 변경 기록 저장 | 기록 보관 + 다른 사람과 공유·협업 |

## 2. 저장소(Repository) 만들고 기록하기

* **저장소(Repository)**: Git이 기록을 관리하는 **폴더**. 이 폴더 안의 파일 변화만 Git이 지켜봄.
* 기록은 **"수정 → 담기(add) → 저장(commit)"** 3단계로 이루어짐. 택배로 비유하면 아래와 같음.
  1. **수정**: 보낼 물건(파일)을 준비함.
  2. **`git add`**: 물건을 **택배 상자에 담음** (스테이징, Staging). 아직 보낸 건 아님.
  3. **`git commit`**: 상자를 **테이프로 봉하고 송장(메시지)을 붙임**. 이 순간 하나의 기록이 확정됨.

| 명령어 | 하는 일 |
| :--- | :--- |
| `git init` | 지금 폴더를 Git 저장소로 만듦 (처음 한 번만, 숨김 폴더 `.git`이 생김) |
| `git add 파일명` | 변경한 파일을 다음 기록에 포함할 목록(스테이징 영역)에 올림 |
| `git commit -m "내용"` | 스테이징된 변경을 메시지와 함께 하나의 기록으로 저장함 |
| `git log` | 지금까지 저장한 기록을 자세히 보여줌 (누가, 언제, 어떤 메시지로) |
| `git log --oneline` | 기록을 한 줄씩 짧게 보여줌 |

* **왜 add와 commit을 나누는가**: 파일 10개를 고쳤어도 그중 "로그인 기능" 관련 3개만 골라서 한 기록으로 남길 수 있기 때문임. 기록마다 의미가 분명해짐.

## 3. 브랜치(Branch): 평행 세계 만들기

* **한 줄 비유**: 브랜치는 **"평행 세계"** 임. 원래 세계(`main`)는 그대로 두고, 새 세계에서 마음껏 실험해 볼 수 있음.
* **왜 필요한가**: `main`에서 바로 새 기능을 만들다 실수하면 잘 돌아가던 코드까지 망가짐. 브랜치에서 작업하면 실패해도 `main`은 안전함.

| 명령어 | 하는 일 |
| :--- | :--- |
| `git branch 브랜치명` | 새 브랜치를 만듦 (아직 이동은 안 함) |
| `git switch 브랜치명` | 그 브랜치로 이동함 |
| `git switch -c 브랜치명` | 브랜치를 만들고 바로 이동함 (위 두 개를 한 번에) |
| `git merge 브랜치명` | 지금 있는 브랜치에 다른 브랜치의 작업을 합침 |

* **작업 순서 예시**
  1. `git switch -c feature` → `feature`라는 평행 세계를 만들고 그쪽으로 이동함.
  2. 파일 수정 → `git add` → `git commit` → 기록은 `feature` 브랜치에만 쌓임. `main`은 그대로임.
  3. `git switch main` → 원래 세계로 돌아옴.
  4. `git merge feature` → `feature`에서 한 작업을 `main`으로 가져와 합침.

## 4. 원격 저장소와 협업: Clone, Push, Fork, Pull Request

* **원격 저장소(Remote)**: GitHub에 있는 저장소. 내 컴퓨터에 있는 것은 **로컬 저장소**라고 부름.

| 개념 | 비유 | 하는 일 |
| :--- | :--- | :--- |
| `git clone 주소` | 도서관 책을 **통째로 복사**해서 집에 가져오기 | GitHub 저장소 전체(파일 + 기록)를 내 컴퓨터로 내려받음 |
| `git push origin main` | 집에서 쓴 내용을 **사물함에 올려두기** | 내 컴퓨터의 `main` 기록을 원격 저장소(`origin`)에 올림 |
| Fork | 친구 노트를 **복사해서 내 노트로 만들기** | 남의 GitHub 저장소를 내 GitHub 계정으로 복사함 |
| Pull Request (PR) | "내가 고친 부분 확인하고 합쳐 줄래?" **요청서** | 내 브랜치(또는 Fork)의 변경을 원래 저장소에 합쳐 달라고 요청함 |

* **`origin`이 뭔가**: clone할 때 Git이 자동으로 붙여주는 원격 저장소의 **별명**임. 긴 주소 대신 `origin`이라고 부를 수 있음.
* **협업 흐름 (Fork → PR)**
  1. 다른 사람 저장소를 **Fork** → 내 GitHub에 복사본이 생김.
  2. 내 복사본을 **Clone** → 내 컴퓨터로 가져옴.
  3. 브랜치를 만들고 수정 → `add` → `commit`.
  4. **Push** → 내 GitHub 복사본에 올림.
  5. GitHub에서 **Pull Request**를 만듦 → 원래 주인이 확인하고 괜찮으면 합쳐 줌(merge).

## 느낀 점

* 깃허브 사용은 해보았지만 헷갈리던 명령어를 "상자에 담기(add) → 봉하기(commit) → 사물함에 올리기(push)" 순서로 다시 정리하니 흐름이 머릿속에 그려짐
* 브랜치를 평행 세계처럼 쓰면 `main`을 망가뜨릴 걱정 없이 실험할 수 있다는 점이 협업에서 왜 중요한지 알게 됨
